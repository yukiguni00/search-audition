# 既知例外とバックアップ操作領域の検証記録

2026-10-24。基準は前回と同じ main / `c0417fa7797a160b43f0f42e9386ac1865b5a76e`。
データ・描画・ブラウザ回帰テストに加え、以下の既知例外管理と操作領域改善を実施した。

## 変更内容

### 既知例外

`tests/fixtures/known-qualifier-exceptions.json` に次の3件を記録した。

| 公演ID | 芸人名 | 区分 |
| --- | --- | --- |
| 2026-10-15-1600-audition-1st-east | ZAZY | qualifiedPerformers |
| 2026-10-19-1830-audition-1st-east | 烏骨鶏 | qualifiedPerformers |
| 2026-10-20-1830-audition-1st-east | つつがないね | qualifiedPerformers |

理由は「公式合格発表に基づく登録を優先し、既存香盤・合格者情報を保持する」。根拠欄には今回のユーザー確認・指示によること、公式資料の独立再確認は未実施であることを明記した。

`checkEvents` はID・元表記の名前・合格区分の完全一致だけを、出演者一覧への包含判定から除外する。名前の正規化で例外範囲を拡張しない。
通常/追加の混在、重複ID、重複名など、他の整合性チェックは免除しない。
理由・根拠の欠落、例外の重複、未使用になった例外もFAILにする。
登録済みの3組からの増減は専用テストでも検知する。将来の例外追加は公式根拠を確認し、一覧と期待値を意図的に更新する必要がある。
出演者一覧が未確認の空配列を包含判定の対象外とする従来の扱いは維持した。これは一覧未確認を「完全に整合済み」と認定するものではない。

他クラスのボタンにはCSSを適用しない。1280/390/375/320pxの初期画面を目視確認した。

### 架空不一致のFAIL確認

Nodeテスト内で本番JSONをメモリに複製し、以下をすべて `assert.throws` で確認した。

- 既知例外と同じ公演に別の架空合格者を追加する。
- 別公演に架空合格者を追加する。
- それぞれ通常合格/追加合格の両方で試す。
- 既知の芸人名を別公演IDに移す、元表記を変える、通常から追加区分へ移すとFAIL。
- 既知例外と同じ名前でも通常/追加の重複ならFAIL。
- 元の不一致が解消したら未使用例外としてFAIL。

独立プロセスでも `tests/helpers/unknown-qualifier-probe.cjs` を実行した。
このスクリプトはメモリ内の `2026-10-15-1600-audition-1st-east` に `架空の未登録合格者_TEST_ONLY` を追加し、実際のチェック関数を呼ぶ。
例外で握りつぶされず「出演者にいない合格者」となり、実際に終了コード1になった。
本番JSONへの書き込みはない。
